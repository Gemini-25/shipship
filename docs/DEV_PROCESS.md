# 개발 과정 (2026-10-16 새로 정함)

## 왜 바꿨나
- 전체 회귀 52번을 세어 보니 시험 136개 중 **90개가 통과했다 실패했다 오락가락**했다 (늘 통과 40 · 늘 실패 6).
- 장면 시험은 "하루를 보낸 배 전체"를 몇 시간 통째로 돌린 뒤 결과를 문턱으로 본다 → 어디서든 행동이 조금 바뀌면 역사가 갈려 상관없는 시험이 뒤집힌다.
- 기능 하나마다 10~30개가 뒤집히고, 그걸 하나씩 "진짜냐 운이냐" 가리는 데 개발 시간 · 토큰의 대부분이 들었다.
- CPU는 더 짜낼 게 적다: .NET 실행 설정 7가지는 오차(±10%) 안 · 프로파일은 평평(가장 큰 항목 7%) · 첫날 배 캐시로 −17%.

## 시험의 세 층 (`tools/tests/tests.txt`)
| 층 | 무엇 | 실패하면 |
|---|---|---|
| **rule** 규칙 시험 (`--ruletest`) | 작은 배에서 규칙 하나씩 — 몇 초 · 결정적 | **막음** — 진짜 버그 |
| **core** 핵심 장면 15개 | 회귀 52번 내내 통과하던 것 | **막음** — 바로 조사 |
| **scene** 장면 시험 (나머지) | 이야기 장면 · 통계 | 막지 않음 — 기준(`tools/tests/baseline.txt`)에선 통과하던 장면이 실패하면 다른 시드 둘(11 · 23)로 다시 돌려 **거기서도 실패할 때만 조사** |

- 끄는 시험은 없다. 장면 시험도 늘 돌고 결과표에 남는다.
- 새 기능 · 고친 버그마다 규칙 시험을 하나씩 더한다 (`tools/Headless/RuleTests.cs`). 규칙은 고치기 전 코드에서 실패하는지 확인한다.

## 언제 · 어디서
| 언제 | 무엇 | 걸리는 시간 |
|---|---|---|
| 기능 하나 넣을 때마다 | 빌드 + 그 기능 시험 + **`tools/quick.sh`** (규칙 + 핵심 15) | 약 3분 |
| 푸시마다 (자동) | **GitHub Actions** `tests` — 전체 138개를 5조각 동시에 (이 계정은 작업을 동시에 5개까지), 새 실패는 다른 시드로 재확인, 한 장 요약 | **17분 30초** (첫 실행 12조각 22분 — 줄 서기 5분 → 5조각) · 가장 긴 growthtest(약 15분)가 정함 |
| 묶음 끝 | 그 사이 Actions 요약을 읽고 정리 · 조사 필요한 것만 조사 · `baseline.txt` 갱신 · README · 보고 | — |

- 결과는 긴 출력 대신 **요약 한 장**만 읽는다 (Actions: report 작업 로그 끝 30줄에 한 줄 요약 · 빨강 · 조사 필요) (`tools/ci/summarize.py` — Actions 작업 요약 · `summary` 아티팩트 · `build/quick/summary.md`).
- 보고는 중간엔 한 줄, 묶음 끝에 결과표와 함께 자세히.

## 도구
- `tools/quick.sh [출력 폴더] [더 돌릴 시험 ...]` — 빠른 묶음
- `tools/ci/run-tests.sh 목록 출력 [동시에] [시드] [뒤붙임]` — 시험 여러 개를 돌려 이름별 파일로
- `tools/ci/shard.py tests.txt 조각 조각수` — 오래 걸리는 것부터 고르게 나눔
- `tools/ci/summarize.py --results 폴더 [--recheck 폴더] [--plan json] [--md 파일] [--only rule,core]` — 한 장 요약 (빨강이면 종료 코드 1)
- 첫날 배 캐시는 기본 켬 (`SHIPSIM_WARM=0`으로 끔) · 켬/끔 출력이 137개 모두 같음을 확인했다.
